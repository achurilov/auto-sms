## 1) Цели и ограничения проекта
**Цель:** мобильное приложение для массовой отправки SMS по контактам, сгруппированным на сервере.  
**Пользователь:** выбирает 1+ групп, вводит текст и отправляет.  
**Администратор (вне приложения):** создает/наполняет группы на сервере.  
**Канал отправки:** через SIM-карту телефона (SMS API ОС, не через SMS-шлюз).

**Ключевые ограничения/риски:**
- На Android отправка SMS через SIM возможна при наличии разрешений; на iOS автоматическая массовая отправка SMS **сильно ограничена** (как правило, только через UI-композер, без «тихой» рассылки). Практически проект ориентировать на **Android** или закладывать разные режимы на iOS.
- Требования комплаенса: согласие получателей, антиспам, логирование, возможность отписки/стоп-слова (если нужно).

---

## 2) Роли и пользовательские сценарии
### Мобильное приложение (пользователь)
1. Вход/авторизация.
2. Синхронизация списка доступных групп.
3. Выбор одной/нескольких групп.
4. Просмотр количества получателей (и, опционально, превью списка).
5. Ввод текста сообщения (счетчик символов/частей SMS).
6. Отправка: приложение формирует очередь и отправляет SMS через SIM.
7. Экран прогресса: отправлено/ошибка/повторить.
8. История рассылок (что, когда, в какие группы, результаты).

### Админ-панель/сервер (администратор)
- CRUD групп.
- Импорт контактов (CSV/XLSX), валидация номеров.
- Управление доступом пользователей к группам (по ролям/организациям).
- Просмотр статистики рассылок (по пользователю/группе/периоду).

## 3) Функциональные требования (MVP)
### Мобильное приложение
- Авторизация (логин/пароль или SSO/OTP).
- Список групп (полученных с сервера), поиск/фильтр.
- Мультивыбор групп.
- Поле ввода сообщения + шаблоны (опционально).
- Подсчет длины, предупреждение о нескольких частях SMS.
- Отправка через SIM:
  - постановка в очередь,
  - прогресс и статусы (sent/delivered если доступно),
  - обработка ошибок (нет сети/нет разрешений/нет SIM/лимиты оператора).
- Локальное хранение истории отправок (и синхронизация на сервер при наличии сети).

### Сервер
- REST/GraphQL API:
  - получить список групп, доступных пользователю,
  - получить состав групп (номера телефонов),
  - принять отчет о рассылке (статусы/ошибки).
- БД: пользователи, группы, контакты, связи, рассылки, результаты.

---

## 4) Нефункциональные требования
- Безопасность: TLS, JWT/refresh, контроль доступа к группам.
- Надежность: очередь отправки, повторные попытки, работа при потере сети (offline-first для истории).
- Производительность: загрузка контактов пачками, пагинация, кэширование групп.
- Наблюдаемость: логи/трассировка на сервере, краш-репорты в приложении.
- Масштабируемость: группы могут содержать тысячи контактов → нужны батчи и ограничения.

---

## 5) Архитектура решения
### Клиент (Android приоритетно)
- UI: список групп → экран создания рассылки → прогресс → история.
- Слой данных:
  - API клиент,
  - локальная БД (Room) для кэша групп и истории,
  - менеджер очереди отправки.
- Слой отправки SMS:
  - использование `SmsManager` (Android),
  - фоновые задачи (WorkManager) для гарантированной отправки и ретраев,
  - прием статусов через `BroadcastReceiver` (SENT/DELIVERED).

### Сервер
- API сервис (например, Node.js/NestJS, Java/Spring, Python/FastAPI).
- База данных (PostgreSQL).
- Админка (например, отдельный web-интерфейс или готовая админ-панель).
- Хранилище аудита и событий.

## 6) Проработка Android-разрешений и UX
- Разрешения: `SEND_SMS`, `READ_PHONE_STATE` (по необходимости), возможно `RECEIVE_SMS` не требуется, если только статусы отправки.
- UX-поток разрешений: объяснение, зачем нужно, отказ → режим «только подготовка» без отправки.
- Ограничения ОС/оператора:
  - лимиты на количество SMS в единицу времени,
  - возможные подтверждения у ОС при массовой отправке,
  - учитывать dual-SIM (выбор SIM для отправки).

## 8) API (минимальный набор)
- `POST /auth/login` → token
- `GET /groups` → список групп (доступных пользователю)
- `GET /groups/{id}` → детали + количество (по умолчанию без полного списка)
- `GET /groups/{id}/contacts?cursor=...` → контакты батчами
- `POST /send-jobs` → регистрация рассылки (группы, текст)
- `POST /send-jobs/{id}/events` → загрузка статусов отправки (батч)

*Примечание:* можно не создавать `send-jobs` заранее, но это удобно для аудита и статистики.

## 9) Логика отправки (алгоритм)
1. Пользователь выбирает группы.
2. Приложение получает контакты групп (с дедупликацией номеров).
3. Создается локальная очередь отправки (со статусами).
4. WorkManager запускает отправку:
   - отправка батчами,
   - задержки/троттлинг (например, N SMS в минуту),
   - фиксация результата в локальной БД,
   - периодическая синхронизация статусов на сервер.
5. UI показывает прогресс и позволяет:
   - пауза/продолжить,
   - повторить ошибки,
   - отменить рассылку.

## 10) Админка (минимум)
- Логин админа.
- Управление группами: создать/переименовать/архивировать.
- Импорт контактов в группу (CSV), проверка формата, нормализация в E.164.
- Назначение групп пользователям/организациям.
- Просмотр истории рассылок (по пользователям и группам).

## 11) Тестирование
- Юнит-тесты: форматирование номеров, дедупликация, разбиение на части SMS.
- Интеграционные: API, авторизация, пагинация контактов.

- Нагрузочные тесты сервера: выдача контактов большими группами, прием событий.

## 12) План работ по этапам (пример)
### Этап 0 — Аналитика (3–7 дней)
- Уточнить целевые платформы (Android-only или Android+iOS).
- Уточнить требования комплаенса, лимиты рассылок, нужна ли доставка (delivery reports).
- Прототип UI (Figma).

### Этап 1 — Сервер MVP (1–2 недели)
- Авторизация, пользователи.
- Группы/контакты, импорт.
- API выдачи групп и контактов.
- Базовый аудит.

### Этап 2 — Мобильное приложение MVP (2–4 недели)
- Авторизация.
- Экран групп (мультивыбор).
- Экран сообщения + счетчик.
- Очередь отправки через SIM (WorkManager), прогресс.
- История рассылок локально.

### Этап 3 — Синхронизация результатов и админ-отчеты (1–2 недели)
- Отправка событий на сервер.
- Просмотр статистики в админке.
- Улучшение ошибок/ретраев/паузы.

### Этап 4 — Полировка и релиз (1–2 недели)
- Безопасность, нагрузка, UX разрешений.
- Подготовка к публикации (если планируется Google Play), документация.
