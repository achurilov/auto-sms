**Анализ требований**

*   **Пользователь:** Сотрудник компании (например, курьер, менеджер), использующий корпоративный смартфон. Не является техническим специалистом.
*   **Основная цель пользователя:** Быстро отправить одинаковое СМС-сообщение группе клиентов или сотрудников через SIM-карту своего телефона.
*   **Ключевые ограничения:**
    *   Отправка должна происходить именно с номера телефона пользователя (через его SIM-карту), а не через сторонние SMS-шлюзы. Это критично для доверия получателей и обратной связи.
    *   Пользователь не управляет контактами и группами. Он только выбирает из готового списка.
    *   Интерфейс должен быть максимально простым, рассчитанным на выполнение одной задачи в 2-3 клика.
*   **Функциональные требования:**
    1.  Авторизация пользователя в приложении (логин/пароль).
    2.  Получение актуального списка групп контактов с сервера.
    3.  Выбор одной или нескольких групп для рассылки.
    4.  Ввод текста сообщения. Отображение счетчика символов (лимит 70/160) и предполагаемого количества частей СМС.
    5.  Отправка сообщений поочередно через нативный API устройства (`SmsManager` на Android, `MFMessageComposeViewController` на iOS).
    6.  Отображение статуса отправки для каждого контакта («Отправлено», «Ошибка»).
*   **Нефункциональные требования:**
    *   Производительность: список групп и контактов должен загружаться за <2 секунды при хорошем 3G/4G соединении.
    *   Безопасность: хранение токена авторизации в защищенном хранилище ОС (*Keychain* / *EncryptedSharedPreferences*). Передача данных только по HTTPS.
    *   Работа в оффлайн: просмотр ранее загруженных групп возможен без интернета. Отправка — только при наличии сети и сигнала оператора.

**Архитектура системы**

Система состоит из трех основных компонентов:
1.  **Мобильное приложение (Client):** Фронтенд для конечного пользователя. Реализует UI/UX, логику выбора контактов и инициирует отправку СМС.
2.  **Серверная часть (Backend API):** Предоставляет REST API для мобильного приложения. Отвечает за аутентификацию пользователей и отдачу справочника групп и контактов.
3.  **Панель администратора (Admin Panel):** Веб-интерфейс для управления пользователями, создания/редактирования групп и наполнения их контактами. Может быть частью серверного бэкенда.

**Схема взаимодействия:**
`[Мобильное приложение] <--HTTPS/REST--> [API Gateway] <---> [Сервисы Бэкенда] <---> [База Данных]`
`[Мобильное приложение] --(Android/iOS SmsManager)--> [SIM-карта] --> [Оператор связи]`

**Технологический стек**

*   **Мобильное приложение:**
    *   Подход: Кросс-платформенная разработка на **Flutter**. Обоснование: единая кодовая база ускоряет разработку на ~30%, обеспечивает нативное качество интерфейса на обеих платформах, имеет готовые плагины для работы с СМС и сетью.
    *   Состояние: **Riverpod** или **BLoC** для предсказуемого управления состоянием.
    *   Сеть: Пакет `dio` с поддержкой интерсепторов для автоматического добавления токена.
    *   Хранение конфигов: `.env` файлы.
*   **Бэкенд API:**
    *   Язык/Фреймворк: **Python + FastAPI**. Обоснование: высокая производительность (асинхронность), автоматическая генерация документации OpenAPI, простота разработки.
    *   Аутентификация: JWT (JSON Web Tokens).
*   **База данных:**
    *   **PostgreSQL**. Надежное реляционное хранилище для связей "пользователь-группа-контакт".
*   **Админ-панель:**
    *   Легковесный веб-интерфесс на **React/Vue.js** или внутренняя админка на базе Django Admin (если бэкенд будет на Django), подключенная к той же БД.

**План разработки**

Этап 1: Проектирование и подготовка (1 неделя)
*   Детальная проработка пользовательских сценариев (Use Cases).
*   Создание интерактивных прототипов UI в Figma (экраны: Логин, Список групп, Экран рассылки, Статус).
*   Проектирование схемы БД ER-диаграмма (таблицы: users, groups, contacts, user_groups_access).
*   Развертывание dev-среды (Git репозиторий, CI/CD пайплайн, staging-сервер).

Этап 2: Разработка Backend API (2 недели)
*   Реализация эндпоинтов: `/auth/login`, `/groups`, `/contacts?group_id=...`.
*   Настройка ролевой модели (роль 'user' может только читать группы/контакты).
*   Написание unit-тестов для бизнес-логики сервисов.
*   Деплой на staging и настройка мониторинга.

Этап 3: Разработка Мобильного приложения (3 недели)
*   Настройка навигации и архитектуры проекта.
*   Экран авторизации, логика хранения/сброса сессии.
*   Экран списка групп с pull-to-refresh и бесконечной прокруткой.
*   Экран составления сообщения: текстовый ввод, счетчик символов, чекбоксы выбора групп.
*   Интеграция с нативными плагинами для отправки СМС (`flutter_sms` или аналоги) и обработка разрешений.
*   Экран со статусом отправки (успех/ошибка для каждого адресата).

Этап 4: Разработка Админ-панели (2 недели, параллельно с Этапом 3)
*   CRUD операции для групп и контактов.
*   Привязка контактов к группам.
*   Управление учетными записями мобильных пользователей.

Этап 5: Сборка, тестирование и запуск (1 неделя)
*   End-to-end тестирование всей цепочки: от создания группы админом до получения СМС на тестовом телефоне.
*   Публикация сборок во внутренние каналы тестирования (TestFlight / Google Play Internal Track).
*   Исправление дефектов.
*   Релиз в App Store и Google Play.

**Тестирование и критерии приёмки**

*   **Модульное тестирование:** Покрытие ключевых функций бэкенда >80%.
*   **Интеграционное тестирование:** Проверка корректности обмена данными между клиентом и сервером (успешная загрузка групп, обработка ошибок сети 4xx/5xx).
*   **UI/UX тестирование:** Проверка верстки на устройствах с разными размерами экранов (от 4" до 6.7").
*   **Приёмочное тестирование (на реальных устройствах):**
    1.  **Кейс:** Пользователь успешно входит в систему.
        *   Критерий: Токен сохранен, переход на главный экран происходит автоматически при повторном запуске.
    2.  **Кейс:** Загрузка списка групп.
        *   Критерий: При плохом интернете показан индикатор загрузки и понятное сообщение об ошибке ("Проверьте соединение"), а не крах приложения.
    3.  **Кейс:** Отправка сообщения 5 контактам.
        *   Критерий: Приложение вызывает системный диалог отправки для каждого из 5 номеров последовательно. В журнале статусов отображено 5 успешных отправок.
    4.  **Кейс:** Попытка отправить сообщение без разрешения на доступ к СМС.
        *   Критерий: Приложение запрашивает разрешение у ОС. Если отказано — кнопка "Отправить" заблокирована с пояснением.
    5.  **Кейс:** Текст сообщения превышает лимит в 3 части СМС.
        *   Критерий: Пользователю показывается предупреждение о стоимости/длине перед отправкой.

**Риски и способы их снижения**

| Риск | Вероятность | Влияние | Способ снижения |
| :--- | :--- | :--- | :--- |
| **Магазины приложений отклонят релиз**, расценив массовую рассылку как спам-инструмент. | Средняя | Высокое | 1. Четко прописать в описании приложения, что это внутренний корпоративный инструмент. 2. Отправка идет строго по одному сообщению через стандартный интерфейс ОС, нет автоматизации обхода ограничений. 3. Подготовить политику конфиденциальности, указывающую, что данные не покидают устройство. |
| **Проблемы с доставкой СМС** (оператор блокирует массовые отправки, абонент вне зоны доступа). | Высокая | Среднее | Технически это вне контроля приложения. Решение: реализовать детальный журнал отправки внутри приложения, чтобы пользователь видел статусы и мог повторить отправку вручную для неудачных номеров. |
| **Изменение политик безопасности ОС** (ограничения на фоновую отправку СМС). | Низкая | Высокое | Мониторинг новостных ресурсов для разработчиков (Android Developers Blog, Apple Developer News). Заложить буфер времени в конце проекта на адаптацию под новые OS версии. |
| **Нестабильная работа кросс-платформенного плагина** для работы с СМС на специфичных прошивках (MIUI, EMUI). | Средняя | Среднее | Провести раннее тестирование на матрице реальных устройств (включая популярные бюджетные китайские смартфоны). Иметь fallback-решение в виде открытия стандартного мессенджера с заполненным номером и текстом. |

**Оценка сроков**

Общий расчетный срок реализации MVP (Minimum Viable Product): **9 недель (~2 календарных месяца)**.

*   Неделя 1: Анализ и проектирование.
*   Недели 2-3: Разработка Backend API.
*   Недели 4-6: Разработка Mobile App (iOS & Android).
*   Недели 4-5 (параллельно): Разработка Admin Panel.
*   Неделя 7: Внутреннее альфа-тестирование, исправление багов.
*   Неделя 8: Бета-тестирование на фокус-группе заказчика.
*   Неделя 9: Релиз и публикация в сторах.

Данная оценка предполагает выделенную команду из 3-х человек: backend-разработчик, mobile-разработчик (full-time на Flutter) и QA-инженер (может работать part-time до Этапа 5).
