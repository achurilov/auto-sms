## Анализ требований

### 1) Роли и сценарии
- **Администратор (веб/сервер)**: создаёт группы, наполняет их контактами, управляет доступом пользователей к группам, просматривает логи рассылок.
- **Пользователь (мобильное приложение)**: выбирает одну/несколько групп, вводит текст, отправляет рассылку через **SIM-карту телефона**, видит прогресс и результат.

### 2) Функциональные требования (Mobile)
1. **Авторизация**: логин/пароль или одноразовый код (MVP — логин/пароль), получение токена.
2. **Список групп** (с сервера):
    - поиск/фильтр;
    - отображение размера группы (кол-во контактов);
    - выбор нескольких групп (multi-select).
3. **Создание рассылки**:
    - поле ввода текста (счётчик символов, предупреждение о сегментации SMS);
    - опция “добавить подпись/префикс” (если нужно — конфиг с сервера);
    - подтверждение отправки (кол-во получателей, примерная длительность).
4. **Отправка через SIM**:
    - очередь сообщений на устройстве;
    - управление скоростью отправки (rate limit, напр. 1 SMS / 2–5 секунд);
    - устойчивость к уходу приложения в фон (foreground service);
    - обработка статусов: отправлено/доставлено/ошибка (по возможности платформы).
5. **Отчёт по рассылке**:
    - общий прогресс (N из M);
    - список ошибок (некорректный номер, отказ сети, нет SIM, нет разрешений);
    - выгрузка/отправка отчёта на сервер.
6. **Офлайн/сбои сети**:
    - группы подгружаются с сервера; при отсутствии сети — использовать последний кэш (read-only);
    - отправка возможна без интернета, но логирование результатов — при появлении сети.

### 3) Функциональные требования (Server/Admin)
1. CRUD групп контактов.
2. Импорт контактов (CSV/XLSX), валидация номеров (E.164/локальные правила).
3. Назначение групп пользователям/ролям.
4. Приём отчётов от мобильного клиента:
    - запуск рассылки (метаданные),
    - прогресс,
    - итоги, ошибки.
5. Аудит: кто/когда/какой текст/какие группы.

### 4) Нефункциональные требования и ограничения
- **Платформа**: реалистично — **Android** (на iOS отправка SMS программно в фоне ограничена политиками OS; возможен только открытый экран “Messages” для каждого SMS).
- **Безопасность**: TLS, JWT/Refresh токены, минимизация хранения персональных данных на устройстве.
- **Производительность**: группы до 10–50 тыс. контактов (реалистично ограничить на MVP, напр. до 5 тыс. на рассылку с устройства).
- **Комплаенс**: пользователь должен иметь законное основание для рассылки; приложение должно фиксировать согласия/назначение — как минимум на уровне регламента и админки.

## Архитектура системы

### 1) Общая схема
- **Mobile (Android)**:
    - UI (выбор групп → текст → отправка),
    - модуль синхронизации групп,
    - локальная БД (кэш групп, очередь рассылок),
    - модуль SMS Sender (через `SmsManager`),
    - модуль статусов (Sent/Delivered receivers),
    - фоновая отправка (Foreground Service + WorkManager для восстановления).
- **Backend API**:
    - Auth сервис (JWT),
    - Groups сервис (выдача групп пользователю),
    - Campaign/Dispatch сервис (приём логов рассылок, отчёты),
    - Admin API (для веб-интерфейса).
- **Admin Web**:
    - управление группами/контактами/доступами,
    - просмотр отчётов.

### 2) Потоки данных
1. Пользователь логинится → получает токен.
2. Mobile запрашивает список доступных групп + метаданные.
3. Пользователь выбирает группы, вводит текст → Mobile создаёт локальную “кампанию”.
4. Mobile запрашивает у сервера **состав групп** (контакты) или получает “снапшот”:
    - Вариант MVP: Mobile получает список номеров (с пагинацией) и пишет в локальную очередь.
    - Вариант расширенный: сервер отдаёт “campaign recipients snapshot id”, а контакты догружаются порциями.
5. Отправка SMS через SIM:
    - каждое SMS фиксируется локально со статусом,
    - периодически/по завершении результаты отправляются на сервер.
6. Админ видит отчёт по кампании.

### 3) Хранение данных
- **Server DB**: users, groups, group_contacts, permissions, campaigns, campaign_recipients (опционально), delivery_reports.
- **Mobile DB (Room)**: cached_groups, cached_group_versions, campaign, campaign_recipient_queue, recipient_status.

### 4) Ограничения Android и обязательные компоненты
- Разрешения: `SEND_SMS`, `READ_PHONE_STATE` (для проверки SIM/оператора), возможно `RECEIVE_SMS` не нужно; для статусов — PendingIntents.
- Foreground Service обязателен для длительных отправок в фоне (Android 8+).
- Rate limiting и обработка “airplane mode/no service”.

## Технологический стек

### Mobile (Android)
- Язык: **Kotlin**
- UI: **Jetpack Compose** (или XML — но Compose быстрее для MVP)
- Архитектура: MVVM + Clean (use cases)
- Локальная БД: **Room**
- Сеть: **Retrofit + OkHttp**
- Фоновые задачи: **WorkManager** + Foreground Service
- DI: **Hilt**
- Логи: Timber + отправка ошибок (Sentry/Firebase Crashlytics)

### Backend
- Язык/фреймворк: **Java/Kotlin + Spring Boot** (или Node.js/NestJS — но для корпоративного контура Spring реалистичнее)
- API: REST + OpenAPI (Swagger)
- Auth: JWT (access+refresh)
- DB: **PostgreSQL**
- Миграции: Flyway
- Очереди (опционально): RabbitMQ/Kafka не обязательны (отправка идёт с телефона), но можно для асинхронной обработки отчётов.
- Хранение файлов импорта: S3-совместимое (MinIO) или локально

### Admin Web
- React + TypeScript (MUI)
- Авторизация через тот же JWT

### DevOps
- Docker Compose (MVP), далее Kubernetes при росте
- CI/CD: GitHub Actions/GitLab CI
- Мониторинг: Prometheus+Grafana (минимум — логирование + health checks)

### Этап 1. Backend MVP (1.5–2 недели)
1. **Auth**
    - POST /auth/login → access/refresh
    - POST /auth/refresh
2. **Группы**
    - GET /groups (для пользователя) → список групп (id, name, count, updatedAt)
    - GET /groups/{id}/contacts?page&size → контакты (phone, name опционально)
    - Версионирование групп (group.updatedAt / version) для кэша
3. **Кампании/отчёты**
    - POST /campaigns (создание: userId, groupIds, messageHash, messageText опционально*)
    - POST /campaigns/{id}/events (batch статусов отправки)
    - GET /campaigns/{id} (сводка)
    - *Если хранить messageText на сервере — обеспечить доступы и аудит.*
4. **Admin API**
    - CRUD групп
    - Импорт CSV (валидация, отчёт об ошибках)
    - Назначение групп пользователям

**Готовность**: Swagger, Postman-коллекция, миграции БД, базовые роли.

---

### Этап 2. Mobile MVP (2.5–3.5 недели)
1. **Каркас приложения**
    - навигация (Compose Navigation),
    - авторизация, хранение токена (EncryptedSharedPreferences).
2. **Экран групп**
    - загрузка групп,
    - multi-select,
    - отображение количества контактов,
    - кэширование в Room.
3. **Экран создания рассылки**
    - ввод текста,
    - подсчёт символов/сегментов,
    - подтверждение отправки.
4. **Загрузка получателей**
    - последовательная загрузка контактов выбранных групп (пагинация),
    - дедупликация номеров (если контакт в нескольких группах),
    - запись очереди в Room.
5. **Отправка SMS**
    - Foreground Service:
        - берёт из очереди следующий номер,
        - отправляет через `SmsManager.sendTextMessage`,
        - записывает статус “sent”/“failed”,
        - rate limit (конфиг из Remote Config/сервера или локально).
    - PendingIntents для `SENT`/`DELIVERED` (где доступно).
    - Обработка ошибок: нет SIM, нет сети, лимиты оператора, нет разрешений.
6. **Экран прогресса/итогов**
    - прогресс-бар, счётчики,
    - список ошибок (первые N, полный — в отчёте),
    - кнопка “повторить неуспешные”.
7. **Синхронизация отчётов**
    - периодическая отправка батчами (например, каждые 20 сообщений или каждые 30 секунд),
    - гарантированная доставка отчёта через WorkManager при появлении сети.

## Тестирование и критерии приёмки

### 1) Виды тестирования
- **Backend**
    - Unit-тесты валидации импорта и прав доступа.
    - Интеграционные тесты API (Testcontainers + Postgres).
    - Нагрузочное: выдача контактов пагинацией (например, 10k контактов).
- **Mobile**
    - Unit-тесты use-cases (дедупликация, очередь).
    - Инструментальные тесты разрешений и фоновой службы (минимум smoke).
    - Ручное тестирование на 3–5 реальных устройствах с SIM разных операторов.
- **E2E**
    - сценарий: создать группу → назначить пользователю → отправить 200–500 SMS → сверить отчёт.

### 2) Критерии приёмки (MVP, измеримые)
1. Пользователь видит **только назначенные** ему группы.
2. Можно выбрать **несколько групп**, получатели **дедуплицируются по номеру**.
3. Приложение отправляет SMS через SIM:
    - при уходе в фон отправка продолжается (Foreground Service),
    - при перезапуске приложения незавершённая рассылка может быть продолжена.
4. Прогресс отображается корректно: отправлено/ошибок/в очереди.
5. Отчёт по рассылке фиксируется на сервере:
    - минимум: delivered/sent/failed (в зависимости от доступности delivered),
    - причины ошибок сохраняются (код/текст).
6. Импорт в админке:
    - файл CSV до N строк (например, 50k) обрабатывается,
    - некорректные номера попадают в отчёт ошибок.
7. Безопасность:
    - токены не пишутся в логи,
    - API закрыто авторизацией и проверкой прав.

## Риски и способы их снижения

1. **Ограничения операторов/антиспам**
    - Риск: блокировка SIM, доставка не гарантирована, лимиты в минуту/сутки.
    - Снижение: rate limit по умолчанию, настройка лимитов на сервере, предупреждение в UI, ограничение размера рассылки, отчётность.

2. **Фоновые ограничения Android**
    - Риск: система убивает процесс, особенно на “агрессивных” прошивках.
    - Снижение: Foreground Service + уведомление, WorkManager для восстановления, инструкции по исключению из энергосбережения (опционально).

3. **Конфиденциальность и хранение контактов**
    - Риск: утечка базы номеров на устройстве.
    - Снижение: хранить на устройстве только очередь текущей кампании, минимальные поля, шифрование БД (SQLCipher) при необходимости, TTL очистки.

4. **Дубли и качество данных**
    - Риск: повторная отправка одному номеру из разных групп.
    - Снижение: нормализация номеров (E.164 или единый формат), дедупликация перед постановкой в очередь.

5. **iOS как требование “в будущем”**
    - Риск: ожидание аналогичной автоматизации на iOS невыполнимо.
    - Снижение: сразу зафиксировать, что iOS-версия возможна только как “полуавтомат” (открытие Messages UI) либо через внешние SMS-шлюзы (не через SIM).

## Оценка сроков

При команде: 1 backend dev, 1 android dev, 1 frontend dev, 1 QA (частично), аналитик/PM (частично).

- Этап 0 (уточнение/проектирование): **0.5 недели**
- Backend MVP: **2 недели**
- Mobile MVP: **3 недели**
- Admin Web MVP: **2 недели** (параллельно с Mobile, добавит ~0.5 недели на интеграции)
- Стабилизация/релиз: **1–1.5 недели**

**Итого до реалистичного запуска MVP: 6–7 недель** календарно (при параллельной работе).
Если нужен пилот без админки (группы руками в БД) — можно выйти на **4–5 недель**, но это ухудшит управляемость и качество данных.
