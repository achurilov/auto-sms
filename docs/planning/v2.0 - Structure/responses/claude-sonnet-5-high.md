# План разработки мобильного приложения для автоматизированной рассылки СМС

## 1. Анализ требований

### 1.1. Функциональные требования

**Мобильное приложение (клиент):**
- Авторизация пользователя (логин/пароль или SSO-токен, выданный администратором)
- Синхронизация списка групп контактов с сервером (просмотр, но не редактирование)
- Мультивыбор групп контактов (чекбоксы, счетчик выбранных контактов)
- Ввод текста сообщения с индикатором количества символов и SMS-частей (160/70 символов на сегмент, кириллица использует UCS-2 → 70 символов)
- Выбор SIM-карты при наличии двух слотов (Dual SIM)
- Постановка рассылки в очередь и отправка через `SmsManager` с контролем скорости (throttling)
- Отображение прогресса рассылки (отправлено/доставлено/ошибка) по каждому контакту
- Локальное логирование результатов и выгрузка отчета на сервер
- Работа в фоне (Foreground Service) для длительных рассылок

**Серверная часть (backend + админ-панель):**
- Административная веб-панель: CRUD групп контактов, импорт контактов (CSV/Excel), назначение групп пользователям
- API для мобильного приложения: аутентификация, получение групп/контактов, отправка отчетов о рассылке
- Хранение истории рассылок (кто, когда, какой группе, текст, статус)
- Разграничение доступа: администратор ↔ пользователь(и) приложения

### 1.2. Критичное техническое ограничение

Прямая отправка SMS через SIM-карту устройства **программно без участия пользователя** возможна только на **Android** (`android.telephony.SmsManager`). На **iOS** Apple не предоставляет публичного API для автоматической отправки SMS — доступен только `MFMessageComposeViewController`, требующий ручного подтверждения пользователем для каждого сообщения и не поддерживающий пакетную отправку.

**Решение:** приложение разрабатывается только под Android. Если требуется iOS-версия — она должна работать через SMS-шлюз (внешний SMS-провайдер с API), а не через SIM-карту устройства. Это решение необходимо зафиксировать с заказчиком на старте, так как влияет на архитектуру.

### 1.3. Нефункциональные требования
- Google Play Policy: приложение с разрешениями SEND_SMS/READ_SMS должно проходить процедуру Sensitive Permissions Declaration и подтверждать core-функциональность (риск отклонения/удаления из Play Store — см. раздел рисков)
- Ограничение операторов связи: не более ~30–100 SMS в час с одной SIM (варьируется по оператору) — защита от антиспам-блокировки номера
- Соответствие 152-ФЗ (если РФ) при хранении телефонов контактов на сервере — шифрование персональных данных, политика хранения
- Поддержка Android 8.0 (API 26) и выше
- Офлайн-режим: очередь рассылки должна сохраняться локально при потере связи с сервером (не требуется для отправки SMS, только для отчетности)

### 1.4. Роли пользователей
| Роль | Возможности |
|---|---|
| Администратор | Веб-панель: создание/редактирование групп, импорт контактов, управление пользователями приложения, просмотр статистики рассылок |
| Пользователь мобильного приложения | Просмотр доступных ему групп, отправка SMS, просмотр истории своих рассылок |

## 2. Архитектура системы

### 2.1. Общая схема

```
[Админ-панель (Web)] ──HTTPS/REST──> [Backend API] <──HTTPS/REST── [Android-приложение]
                                            │
                                      [PostgreSQL]
                                            │
                                      [Redis (кэш/очереди)]
```

### 2.2. Backend
- **REST API** (JWT-аутентификация, refresh-токены)
- Модули:
    - Auth Service (логин, выдача/обновление токенов)
    - Groups Service (CRUD групп, привязка контактов, привязка групп к пользователям)
    - Reports Service (прием статусов доставки от клиента, агрегация статистики)
    - Admin Panel API (отдельные эндпоинты с более широкими правами)
- **База данных (PostgreSQL):** таблицы `users`, `groups`, `contacts`, `group_contacts`, `user_group_access`, `campaigns`, `campaign_recipients_status`
- Хранение телефонов — в зашифрованном виде (AES-256 на уровне столбца) с учетом требований к персональным данным

### 2.3. Мобильное приложение (Android)
Архитектура: **MVVM + Clean Architecture**

```
UI Layer (Jetpack Compose) 
    ↓
ViewModel (StateFlow)
    ↓
UseCase / Domain Layer
    ↓
Repository (Groups, Sending, Auth)
    ↓
├── Remote DataSource (Retrofit → REST API)
└── Local DataSource (Room — кэш групп, очередь отправки, история)
    ↓
SmsSendingEngine (Foreground Service + SmsManager + WorkManager для ретраев)
```

Ключевые компоненты Android-части:
- **Foreground Service** — выполняет саму рассылку, не позволяет системе убить процесс
- **WorkManager** — фоновая догрузка отчетов на сервер при восстановлении сети
- **BroadcastReceiver** — прием `SENT`/`DELIVERED` intent от `SmsManager` для трекинга статуса каждого сообщения
- **Room DB** — локальный кэш групп/контактов (офлайн-доступ) и очередь отправки
- **Rate Limiter** — модуль контроля интервалов между отправками (настраиваемый администратором через серверный конфиг, например 1 SMS/2–3 сек)

### 2.4. Админ-панель
- SPA (React) + backend API, отдельная от мобильного клиента точка входа с ролью admin
- Импорт контактов из CSV/XLSX с валидацией номеров (E.164)

## 3. Технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| Мобильное приложение | Kotlin, Jetpack Compose, MVVM | Нативный доступ к SmsManager, только Android |
| Асинхронность/фон | WorkManager, Foreground Service, Coroutines/Flow | Надежная фоновая отправка, устойчивость к kill-процесса |
| Локальная БД | Room (SQLite) | Кэш групп, очередь, история |
| Сеть | Retrofit + OkHttp, Moshi/kotlinx.serialization | REST-клиент |
| DI | Hilt | Стандарт для Android |
| Backend | Node.js (NestJS) или Java/Kotlin (Spring Boot) | Типизация, готовые модули Auth/RBAC |
| БД сервера | PostgreSQL | Реляционная модель групп/контактов |
| Кэш/очереди | Redis | Кэш сессий, rate-limit конфиги |
| Админ-панель | React + TypeScript, Ant Design | Быстрая разработка CRUD-интерфейсов |
| Аутентификация | JWT (access + refresh) | Стандарт для мобильных клиентов |
| Хостинг | Docker + Kubernetes/Docker Compose (VPS) | Масштабируемость, простое CI/CD |
| CI/CD | GitLab CI / GitHub Actions, Fastlane (для сборки Android) | Автоматизация сборок и деплоя |
| Мониторинг | Sentry (крэши), Prometheus+Grafana (backend) | Отслеживание ошибок отправки |

## 4. План разработки

### Этап 0. Подготовка (1 неделя)
- Согласование ограничения по iOS с заказчиком (фиксация в ТЗ)
- Проектирование БД, API-контрактов (OpenAPI/Swagger)
- Дизайн UI/UX (Figma): экран выбора групп, экран сообщения, экран прогресса рассылки, экран истории

### Этап 1. Backend — базовый функционал (2–3 недели)
- Настройка проекта, БД, миграций
- Auth-модуль (JWT, роли admin/user)
- CRUD API для групп и контактов
- API привязки групп к пользователям
- Заливка тестовых данных

### Этап 2. Админ-панель (2 недели, частично параллельно с Этапом 1)
- Логин администратора
- Управление группами: создание, редактирование, удаление
- Импорт контактов из CSV/XLSX с валидацией номеров
- Управление пользователями приложения и их доступом к группам
- Просмотр статистики/логов рассылок

### Этап 3. Android — базовый каркас (2 недели)
- Настройка проекта, DI, навигация, дизайн-система по Figma
- Экран авторизации, хранение токена (EncryptedSharedPreferences)
- Синхронизация групп с сервером, локальный кэш (Room)
- Экран списка групп с мультивыбором

### Этап 4. Android — модуль отправки SMS (3 недели, ключевой этап)
- Реализация запроса runtime-разрешений (SEND_SMS, READ_PHONE_STATE)
- Экран ввода сообщения, счетчик символов/частей SMS
- Выбор SIM-карты (Dual SIM API)
- Foreground Service для рассылки
- SmsSendingEngine: очередь, Rate Limiter, повторные попытки при ошибке
- BroadcastReceiver для статусов SENT/DELIVERED
- Экран прогресса рассылки в реальном времени (StateFlow → UI)

### Этап 5. Отчетность и история (1,5 недели)
- Отправка результатов рассылки на сервер (WorkManager, с ретраем при отсутствии сети)
- Экран истории рассылок в приложении
- Отображение статистики в админ-панели (доставлено/ошибка/не отправлено)

### Этап 6. Безопасность и соответствие политикам (1,5 недели)
- Шифрование телефонов в БД
- HTTPS/TLS для всех API-запросов, certificate pinning
- Подготовка Data Safety декларации и обоснования Sensitive Permissions для Google Play
- Настройка Privacy Policy, согласия пользователя на обработку данных

### Этап 7. Интеграционное тестирование и стабилизация (2 недели)
- Полный прогон сценариев на реальных устройствах (разные вендоры/версии Android)
- Нагрузочное тестирование backend
- Тестирование на реальных SIM-картах разных операторов (лимиты, задержки)

### Этап 8. Публикация и запуск (1 неделя)
- Прохождение Google Play Review (закладывать риск повторной подачи из-за SMS-разрешений)
- Развертывание production backend
- Пилотный запуск с ограниченной группой пользователей

**Итого: ~15–16 недель (см. раздел «Оценка сроков» с учетом буфера)**

## 5. Тестирование и критерии приёмки

### 5.1. Виды тестирования
- **Unit-тесты:** ViewModel, Repository, Rate Limiter, парсинг SMS-частей (моки SmsManager)
- **Интеграционные тесты backend:** API групп, авторизация, права доступа (user не может редактировать группы)
- **UI-тесты (Espresso/Compose Test):** выбор групп, ввод сообщения, запуск рассылки
- **Ручное тестирование на устройствах:** минимум 3 вендора (Samsung, Xiaomi, Google Pixel) × 2 версии Android, включая Dual SIM устройства
- **Полевое тестирование отправки:** реальные SIM-карты 2–3 операторов, проверка лимитов и антиспам-блокировок
- **Тестирование безопасности:** проверка шифрования, попытки доступа к чужим группам через подмену токена/ID

### 5.2. Критерии приёмки (Definition of Done)
1. Пользователь видит только те группы, которые назначил ему администратор
2. При выборе нескольких групп дубликаты контактов автоматически исключаются
3. Сообщение длиной >160/70 символов корректно разбивается на части, счетчик отображается верно
4. Рассылка 100 контактам завершается без падения приложения, с отображением статуса по каждому получателю
5. При потере интернет-соединения отчет об отправке сохраняется локально и отправляется на сервер после восстановления сети
6. При закрытии приложения во время рассылки Foreground Service продолжает работу до завершения
7. Администратор видит в панели статистику по каждой кампании: доставлено/ошибка/в очереди
8. Приложение проходит модерацию Google Play с одобренным доступом к SEND_SMS

## 6. Риски и способы их снижения

| Риск | Вероятность | Влияние | Способ снижения |
|---|---|---|---|
| Отклонение/блокировка приложения в Google Play из-за политики Sensitive Permissions (SEND_SMS) | Высокая | Критическое | Заранее подготовить обоснование core-функциональности, демо-видео для ревьюеров, рассмотреть публикацию как «управляемое корпоративное приложение» через закрытое распространение (internal app sharing / Managed Google Play) вместо публичного стора |
| Блокировка/пометка номера как спам оператором при массовой рассылке | Высокая | Высокое | Rate Limiter с настраиваемыми интервалами, ограничение количества сообщений в час на SIM, разбивка больших рассылок на батчи с паузами |
| Невозможность реализовать функцию на iOS | Высокая (уже подтверждено) | Среднее | Зафиксировать в ТЗ ограничение Android-only на старте проекта, при необходимости — предложить SMS-шлюз для iOS как отдельную ветку архитектуры |
| Различия в поведении SmsManager на разных вендорских прошивках (MIUI, EMUI и т.д.) | Средняя | Среднее | Расширенное тестирование на устройствах разных производителей, обработка edge-cases (агрессивное управление батареей, kill фоновых процессов) |
| Утечка персональных данных (номера телефонов) | Низкая | Критическое | Шифрование на уровне БД и транспорта, аудит доступа, минимизация хранимых данных на клиенте |
| Изменение политики Google в отношении SMS-разрешений в будущих релизах Android | Средняя | Высокое | Мониторинг Android Developer Blog, закладывать техдолг на возможную миграцию на модель "default SMS app" |
| Задержки из-за интеграции с реальными SIM/операторами (непредсказуемое поведение) | Средняя | Среднее | Ранний прототип модуля отправки (в начале Этапа 4, а не в конце) для выявления проблем заранее |

## 7. Оценка сроков

| Этап | Длительность | Команда |
|---|---|---|
| Подготовка и проектирование | 1 неделя | BA/Analyst, UX-дизайнер |
| Backend (базовый функционал) | 2–3 недели | 1 Backend-разработчик |
| Админ-панель | 2 недели | 1 Frontend-разработчик (частично параллельно) |
| Android — каркас | 2 недели | 1–2 Android-разработчика |
| Android — модуль SMS | 3 недели | 1–2 Android-разработчика |
| Отчетность и история | 1,5 недели | Backend + Android |
| Безопасность и Play Policy | 1,5 недели | Backend + Android + DevOps |
| Тестирование и стабилизация | 2 недели | QA-инженер + вся команда |
| Публикация и запуск | 1 неделя | DevOps, весь состав |
| **Буфер на непредвиденное (Play Review, полевые тесты SMS)** | 2 недели | — |

**Итоговая оценка: 17–18 недель (~4–4,5 месяца)** при команде: 2 Android-разработчика, 1 Backend-разработчик, 1 Frontend-разработчик (админка), 1 QA, 1 UX-дизайнер (частичная занятость), 1 системный аналитик/тимлид.

Возможна параллелизация Backend/Frontend/Android с первой недели после утверждения API-контракта — это позволяет сократить календарный срок до **14–15 недель** при увеличении команды на 1 Android-разработчика.
