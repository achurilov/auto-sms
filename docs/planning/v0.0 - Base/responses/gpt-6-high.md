Для указанного сценария следует разрабатывать **Android-приложение, серверное API и веб-панель администратора**. Пользователь запускает рассылку на телефоне, а сообщения отправляются через выбранную SIM-карту.

Android предоставляет для этого API `SmsManager` и разрешение `SEND_SMS`. На iOS стандартный механизм требует участия пользователя в отправке, поэтому автоматическая рассылка через SIM-карту в предложенном виде для iPhone не подходит. [Android](https://developer.android.com/reference/android/telephony/SmsManager), [Apple](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/SystemMessaging_TopicsForIOS/Articles/SendinganSMSMessage.html).

Ниже — план разработки первой рабочей версии.

1. **Уточнить требования и проверить отправку на реальных телефонах**

   Зафиксировать:

    * максимальное количество получателей одной рассылки и примерный суточный объем;
    * модели телефонов и поддерживаемые версии Android;
    * необходимость выбора SIM-карты на устройствах с двумя SIM;
    * доступность групп: все группы всем пользователям или индивидуальные права;
    * способ установки и обновления приложения.

   Сначала создать небольшой прототип: отправка нескольким получателям, длинные сообщения, выбор SIM, получение результата отправки, работа при заблокированном экране.

   **Результат:** подтвержденная работоспособность на целевых устройствах и согласованные ограничения. Android может ограничивать частоту отправки; допустимый объем также нужно проверить по условиям выбранного оператора.

   Если планируется Google Play, отдельно проверить соответствие политике SMS-разрешений: их использование ограничено, предусмотрены разрешенные сценарии и исключения. Публикацию такого приложения нельзя считать гарантированной. [Правила Google Play](https://support.google.com/googleplay/android-developer/answer/10208820).

2. **Спроектировать архитектуру и данные**

   | Компонент                 | Назначение                                                                                 |
      | ------------------------- | ------------------------------------------------------------------------------------------ |
   | Android-приложение        | Выбор групп, ввод текста, локальная очередь, отправка через SIM, отображение результатов   |
   | Серверное API             | Авторизация, выдача доступных групп и получателей, регистрация рассылок, прием результатов |
   | База данных               | Пользователи, контакты, группы, права доступа, рассылки и их результаты                    |
   | Веб-панель администратора | Управление контактами, группами и пользователями                                           |

   Основные сущности: пользователь, контакт, группа, связь контакта с группой, рассылка, получатель рассылки, попытка отправки.

   При создании рассылки сохранять **снимок списка получателей и текста**. Изменение группы администратором не должно менять уже запущенную рассылку.

3. **Разработать серверное API**

   Реализовать:

    * вход пользователя и проверку прав;
    * получение списка доступных групп с количеством контактов;
    * формирование общего списка получателей выбранных групп;
    * нормализацию телефонных номеров и удаление повторов;
    * создание рассылки с защитой от повторного запроса;
    * прием результатов отправки и получение истории.

   Один номер, встречающийся в нескольких выбранных группах, должен получать сообщение один раз в рамках рассылки.

   Запрет редактирования контактов и групп обычным пользователем необходимо обеспечить на сервере.

4. **Разработать панель администратора**

   Включить:

    * создание, переименование и удаление групп;
    * добавление и редактирование контактов;
    * включение контакта в одну или несколько групп;
    * импорт контактов из CSV с проверкой номеров и отчетом об ошибках;
    * создание и блокировку пользователей;
    * назначение доступа к группам;
    * просмотр истории и результатов рассылок.

   Для контактов предусмотреть признак запрета рассылки, чтобы исключать такие номера при подготовке получателей.

5. **Создать простой интерфейс приложения**

   Основной сценарий:

    * Пользователь входит в приложение.
    * Отмечает одну или несколько групп.
    * Вводит текст сообщения.
    * Видит количество уникальных получателей и количество SMS-сегментов.
    * Выбирает SIM-карту, если доступно несколько.
    * Проверяет итоговые данные и нажимает «Отправить».
    * Наблюдает за прогрессом и результатами.

   Достаточно четырех экранов: вход, новая рассылка, прогресс, история. На экране прогресса предусмотреть паузу и остановку оставшейся очереди. Уже переданные на отправку сообщения отменить нельзя.

6. **Реализовать устойчивую очередь отправки**

   Это основная техническая часть приложения:

    * сохранять очередь и результаты локально на телефоне;
    * отправлять сообщения последовательно с настраиваемым интервалом;
    * учитывать разделение длинного текста на несколько SMS и результаты каждой части;
    * обрабатывать отсутствие сети, недоступную SIM, отказ в разрешении и системные ограничения;
    * сохранять прогресс при закрытии приложения и перезапуске телефона;
    * предусмотреть выполнение при свернутом приложении с учетом ограничений Android;
    * синхронизировать результаты с сервером после восстановления интернета.

   Для каждого получателя отображать состояния: «В очереди», «Отправляется», «Отправлено», «Доставлено», «Ошибка», «Результат неизвестен», «Отменено».

   **«Отправлено» и «Доставлено» — разные результаты.** Отметку доставки устанавливать только при получении соответствующего отчета; его отсутствие не означает ошибку отправки. Android предоставляет отдельные уведомления об отправке и доставке. [Документация SmsManager](https://developer.android.com/reference/android/telephony/SmsManager).

   При сбое между передачей SMS системе и сохранением результата возможна неопределенность. Такие сообщения не следует автоматически отправлять повторно: пользователь должен видеть риск дублирования.

7. **Обеспечить защиту данных**

   Реализовать HTTPS, безопасное хранение токенов, разграничение доступа и журнал действий администратора. Не выводить телефонные номера и тексты сообщений в технические логи без необходимости.

   Контакты хранить во внутреннем хранилище приложения, без добавления в телефонную книгу. Определить сроки хранения локальных данных и истории рассылок.

8. **Провести тестирование и пилотный запуск**

   Проверить:

    * пересекающиеся и пустые группы, некорректные номера;
    * кириллицу, латиницу, эмодзи и длинные сообщения;
    * одну и две SIM-карты;
    * потерю интернета отдельно от потери мобильной связи;
    * блокировку экрана, завершение процесса и перезагрузку;
    * повторное нажатие «Отправить» и повторную синхронизацию;
    * паузу, отмену и обработку неизвестных результатов;
    * рассылку согласованного объема на целевых устройствах.

   После этого провести пилот с небольшой группой пользователей, подготовить инструкцию и настроить резервное копирование сервера.

Предлагаемый стек: **Kotlin + Jetpack Compose** для Android, **Room** для локальной очереди, **Spring Boot + PostgreSQL** для серверной части и **React** для панели администратора.

Ориентировочная трудоемкость MVP для одного опытного разработчика:

| Этап                                | Рабочие дни |
| ----------------------------------- | ----------: |
| Требования и технический прототип   |         3–5 |
| Проектирование и серверное API      |         5–8 |
| Панель администратора               |         4–6 |
| Интерфейс приложения                |         5–7 |
| Очередь, отправка и восстановление  |        7–10 |
| Тестирование, пилот и развертывание |         5–8 |
| **Всего**                           |   **29–44** |

Это предварительная оценка — примерно **6–9 рабочих недель**, без учета ожидания публикации в магазине. Уточнять ее следует после проверки отправки на выбранных телефонах и согласования объемов рассылки.
