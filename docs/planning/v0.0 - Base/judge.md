# Исходная задача, на которую были даны ответы

```
Напиши план разработки мобильного приложения для автоматизированной рассылки СМС сообщений.
В приложении должен быть простой интерфейс, позволяющий выбрать одну или несколько групп контактов, ввести текст сообщения и отправить его всем контактам через SIM-карту телефона.
Группы контактов хранятся на сервере, создает и заполняет их администратор. Пользователь мобильного приложения только использует готовые группы. 
```

# Критерии оценки

Оцени каждый ответ по следующим критериям (0-4 балла за каждый)

**1. Структурность и логика**

Оцениваются последовательность этапов, их взаимосвязь и понятность изложения.

* **0 баллов** — хаотичный текст без выделенных этапов.
* **1 балл** — перечислены отдельные задачи, но последовательность разработки не прослеживается.
* **2 балла** — выделены основные этапы, но их порядок или взаимосвязи раскрыты недостаточно.
* **3 балла** — представлен последовательный план: от уточнения требований и проектирования до разработки, тестирования и выпуска.
* **4 балла** — у каждого этапа обозначен результат, показаны зависимости между задачами и условия перехода к следующему этапу.

**2. Конкретика и выполнимость задач**

Оценивается, можно ли использовать план для постановки задач и контроля выполнения работ.

* **0 баллов** — ответ состоит из общих рассуждений о разработке.
* **1 балл** — есть действия вроде «разработать приложение» или «создать сервер», но их содержание не раскрыто.
* **2 балла** — перечислены конкретные функции и задачи, но ожидаемые результаты описаны частично.
* **3 балла** — задачи достаточно подробно раскрыты, обозначены результаты и способы проверки ключевых функций.
* **4 балла** — задачи можно передать исполнителям: понятны содержание работ, необходимые инструменты или подходы, результаты и критерии готовности.

**3. Полнота и обоснованность технической проработки**

Оценивается, охватывает ли план существенные части продукта и объясняет ли предлагаемые решения.

* **0 баллов** — техническая сторона практически отсутствует или противоречит назначению продукта.
* **1 балл** — перечислены отдельные технологии или экраны без объяснения их взаимодействия.
* **2 балла** — описаны основные компоненты и функции, но пропущены существенные вопросы: например, хранение данных, интеграции, права доступа или тестирование.
* **3 балла** — охвачены необходимые компоненты, пользовательские сценарии, данные, интеграции, безопасность, тестирование и выпуск; ключевые решения объяснены.
* **4 балла** — дополнительно разобраны сложные сценарии и ошибки, технические риски и компромиссы; предусмотрены эксплуатация и сопровождение в объёме, соответствующем проекту.

**4. Реалистичность и приоритизация**

Оценивается, учитывает ли план ограничения проекта и позволяет ли получить результат с доступными ресурсами.

* **0 баллов** — план основан на невыполнимых предположениях или игнорирует критические ограничения.
* **1 балл** — отдельные задачи выполнимы, но объём работ, сроки или технические возможности явно переоценены.
* **2 балла** — план в целом осуществим, однако приоритеты, ресурсы и зависимости проработаны слабо.
* **3 балла** — выделен минимально необходимый объём продукта, учтены основные ограничения, ресурсы и внешние зависимости; оценки имеют понятные основания.
* **4 балла** — предусмотрены ранняя проверка рискованных предположений, поэтапный выпуск и меры на случай проблем; неопределённости явно обозначены, а сроки и ресурсы согласованы с объёмом работ.

**5. Следование инструкциям и требованиям**

Оценивается соответствие плана исходному заданию, формату и ограничениям.

* **0 баллов** — предложен план другого продукта либо проигнорированы ключевые требования.
* **1 балл** — учтены отдельные требования, но значительная часть задания пропущена или искажена.
* **2 балла** — основные требования отражены, однако есть существенные пропуски или необоснованные изменения объёма проекта.
* **3 балла** — все ключевые требования соблюдены; присутствуют лишь небольшие неточности.
* **4 балла** — полностью соблюдены требования и формат; обязательные функции отделены от предложений по развитию, недостающие сведения обозначены как вопросы или допущения.

# Правила оценки

* оцени строго по критериям, не ориентируясь на объём текста;
* не отдавай предпочтения более длинным ответам только за счёт длины;
* если несколько ответов похожи по качеству, допускается одинаковая оценка;
* будь максимально нейтрален.

* таблица с баллами по каждому критерию;
* итоговая сумма (из 20);
* краткое обоснование (3-5 предложений на каждый ответ).

# План разработки мобильного приложения "СМС-Рассылка"

## 1. Этап анализа и планирования (Discovery Phase)
**Цель:** Сформировать четкое видение продукта, определить его границы и технические требования.

*   **1.1. Определение целевой аудитории:**
    *   Малый бизнес (кафе, салоны красоты, магазины).
    *   Организаторы мероприятий.
    *   Руководители небольших коллективов.
*   **1.2. Формирование User Stories (Пользовательские истории):**
    *   Как пользователь, я хочу видеть список доступных мне групп контактов, чтобы выбрать получателей рассылки.
    *   Как пользователь, я хочу видеть количество контактов в выбранной группе, чтобы понимать охват.
    *   Как пользователь, я хочу вводить текст сообщения с счетчиком символов (ограничение SMS — 70/160 знаков), чтобы контролировать стоимость.
    *   Как пользователь, я хочу отправлять сообщение через свою SIM-карту, чтобы не платить за сторонние сервисы.
    *   Как пользователь, я хочу видеть статус отправки ("Отправлено", "Ошибка"), чтобы убедиться в успешной доставке.
*   **1.3. Функциональные требования:**
    *   Авторизация пользователя по логину/паролю.
    *   Получение списка групп контактов с сервера.
    *   Отображение списка групп с возможностью множественного выбора.
    *   Поле для ввода текста сообщения.
    *   Кнопка "Отправить".
    *   Экран статуса отправки.
*   **1.4. Нефункциональные требования:**
    *   Простой и интуитивно понятный интерфейс.
    *   Работа на Android и iOS (кросс-платформенная разработка выглядит предпочтительной).
    *   Безопасность передачи данных между приложением и сервером (HTTPS).
*   **1.5. Архитектура системы:**
    *   Мобильное приложение (клиент).
    *   Backend-сервер (API) для управления группами пользователей и контактами.
    *   База данных (например, PostgreSQL) на сервере.

## 2. Проектирование UI/UX
**Цель:** Создать простой и удобный интерфейс без лишних элементов.

*   **2.1. Карта экранов (Screen Flow):**
    1.  `Экран авторизации` -> 2. `Экран списка групп` -> 3. `Экран создания рассылки` -> 4. `Экран статуса`.
*   **2.2. Прототипирование (Wireframing):**
    *   **Экран списка групп:** Список чекбоксов с названием группы и количеством контактов (например, `[ ] Клиенты (- 150)`). Вверху поле поиска. Внизу кнопка "Далее".
    *   **Экран создания рассылки:** На верхней части экрана отображаются выбранные группы (можно нажать крестик, чтобы удалить). Основное пространство занимает многострочное поле для ввода текста. Под ним — счетчик символов (например, "Символов: 45 / 1 часть"). В самом низу — большая кнопка "ОТПРАВИТЬ ВСЕМ".
    *   **Экран статуса:** Список из имен контактов (или номеров) со статусом напротив каждого ("✅ Отправлено", "❌ Ошибка").
*   **2.3. Дизайн-концепция (Mockups):** Разработка визуального стиля в минималистичном ключе. Основной акцент на читаемость и удобство нажатия на кнопки.

## 3. Разработка Backend (Серверная часть)
**Цель:** Обеспечить работу API для мобильного приложения и интерфейса администратора.

*   **3.1. Технологический стек:** Node.js + Express / Python + Django / Go. База данных — PostgreSQL.
*   **3.2. Разработка API-эндпоинтов:**
    *   `POST /api/login`: Аутентификация пользователя.
    *   `GET /api/groups`: Возвращает JSON-список групп, доступных пользователю.
        ```json
        [
          { "id": 1, "name": "VIP-Клиенты", "contact_count": 25 },
          { "id": 2, "name": "Рассылка_октябрь", "contact_count": 150 }
        ]
        ```
*   **3.3. Административная панель (Web-интерфейс):**
    *   Создание/удаление пользователей приложения.
    *   Создание/редактирование/удаление групп контактов.
    *   Массовая загрузка контактов в группу (через CSV-файл).
*   **3.4. Модель базы данных:** Таблицы `Users`, `Groups`, `Contacts`, `User_Groups` (связь многие-ко-многим).

## 4. Разработка Frontend (Мобильное приложение)
**Цель:** Реализовать клиентскую часть согласно дизайну.

*   **4.1. Выбор технологии:**
    *   **Кросс-платформенная (*рекомендуется*):** Flutter или React Native. Позволит быстрее выпустить приложение под обе платформы с единым кодом.
    *   **Нативная:** Swift (для iOS) и Kotlin (для Android). Потребует больше ресурсов.
*   **4.2. Ключевые модули для разработки:**
    *   **Модуль авторизации:** Форма входа, сохранение токена сессии.
    *   **Модуль работы с сетью:** Сервисы для выполнения запросов к API (`login()`, `fetchGroups()`).
    *   **Экран "Группы":** Отображение списка, логика множественного выбора, запрос к API при открытии экрана.
    *   **Экран "Рассылка":**
        *   Приём ID выбранных групп с предыдущего экрана.
        *   Отображение названий выбранных групп.
        *   Поле ввода `TextField` с обработчиком изменений для счетчика символов.
        *   Логика сборки финального текста.
    *   **Интеграция с телефонией:** Самый ответственный модуль. Использование нативных возможностей ОС для отправки SMS:
        *   **Android:** Интент `ACTION_SENDTO` с URI `smsto:`. Это откроет стандартное приложение для СМС с уже заполненными получателями и текстом. Пользователь нажмет кнопку "Отправить" сам. Это самый безопасный и соответствующий правилам Google Play метод.
        *   **iOS:** Apple не предоставляет публичного API для прямой программной отправки SMS. Единственный легальный способ — использовать фреймворк `MessageUI` и контроллер `MFMessageComposeViewController`. Он также открывает системный интерфейс сообщений с предзаполненными данными.
*   **4.3. Модуль "Статус":** Так как отправка идет через системное приложение, точное получение статуса доставки затруднено. Можно реализовать ручной ввод результатов или оставить этот экран как подтверждение того, что данные были переданы в системное приложение для отправки.

## 5. Тестирование (QA)
**Цель:** Гарантировать стабильность и корректность работы приложения.

*   **5.1. Модульное тестирование:** Проверка отдельных функций (например, правильно ли работает счетчик символов).
*   **5.2. Интеграционное тестирование:** Проверка взаимодействия между модулями (приложение <-> API).
*   **5.3. Тестирование UI/UX:** Проверка удобства использования на разных экранах и размерах устройств.
*   **5.4. Тестирование на реальных устройствах:** Обязательная проверка функции отправки SMS на нескольких физических телефонах с Android и iOS.
*   **5.5. Нагрузочное тестирование API:** Симуляция одновременной работы нескольких десятков пользователей.

## 6. Релиз и публикация
**Цель:** Опубликовать приложение в сторах.

*   **6.1. Подготовка маркетинговых материалов:** Скриншоты, иконка, описание.
*   **6.2. Публикация в App Store и Google Play:** Прохождение ревью. Особое внимание нужно уделить описанию функции отправки SMS, чтобы модераторы поняли, что приложение не отправляет сообщения скрыто, а использует стандартный интерфейс телефона.

**Пример кода отправки СМС (Kotlin):**
```kotlin
fun sendSmsToContacts(contacts: List<Contact>, message: String) {
    val smsManager = SmsManager.getDefault()
    contacts.forEach { contact ->
        try {
            val parts = smsManager.divideMessage(message)
            smsManager.sendMultipartTextMessage(
                contact.phoneNumber,
                null,
                parts,
                null,
                null
            )
            // Задержка между отправками для избежания спам-фильтров
            Thread.sleep(200)
        } catch (e: Exception) {
            // Логирование ошибки для данного контакта
        }
    }
}
```

## 5. Обработка edge-кейсов и ограничений

- **Разрешения Android:** запрос runtime-разрешений SEND_SMS (Android 6.0+)
- **Ограничения оператора:** лимиты на количество СМС в сутки (некоторые операторы блокируют >30-100 СМС/сутки с одной SIM)
- **Двойная SIM-карта:** дать пользователю выбор, через какую SIM отправлять
- **Оффлайн-режим:** кэширование групп контактов локально (Room), чтобы приложение работало без интернета для отправки (только загрузка групп требует сети)
- **Дублирование номеров:** если контакт входит в несколько выбранных групп — дедупликация перед отправкой
- **Длинные сообщения:** разбивка на несколько частей (multipart SMS)

## ⚠️ Важные ограничения, которые стоит учесть заранее

1. **iOS не поддерживается** для программной отправки СМС — только Android
2. **Google Play Policy** ограничивает использование SEND_SMS permission — нужно либо стать SMS-по-умолчанию приложением, либо распространять вне Play Store
3. **Ограничения операторов** на количество СМС в сутки с одной SIM-карты
4. **Стоимость СМС** ложится на баланс SIM-карты пользователя (не через SMS-шлюз/агрегатор)

Если планируются большие объемы рассылки, стоит рассмотреть альтернативу — интеграцию с SMS-шлюзом (SMS-агрегатором) вместо отправки через SIM-карту телефона.
