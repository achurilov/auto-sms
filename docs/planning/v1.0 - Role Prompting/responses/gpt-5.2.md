Ниже — план разработки мобильного приложения для автоматизированной SMS‑рассылки через SIM‑карту устройства, с группами контактов, управляемыми на сервере администратором. План ориентирован на практическую реализацию (Android приоритетно, iOS — с оговорками).

---

## 1) Уточнение требований и ограничений (Discovery)

### 1.1. Бизнес‑сценарии (MVP)
1. Пользователь авторизуется в приложении.
2. Приложение получает с сервера список доступных групп.
3. Пользователь выбирает 1+ групп.
4. Пользователь вводит текст сообщения (шаблон/без шаблонов).
5. Пользователь запускает отправку.
6. Приложение отправляет SMS всем контактам выбранных групп через SIM телефона.
7. Пользователь видит прогресс и итог (сколько отправлено/ошибки).
8. Сервер получает статусы (по возможности) и хранит историю рассылок.

### 1.2. Важные ограничения платформ
- **Android**: отправка SMS через SIM возможна, но нужны runtime‑permissions (SEND_SMS, READ_PHONE_STATE опционально, READ_SMS/RECEIVE_SMS — только если нужно подтверждать доставку/читать входящие). С Android 4.4+ есть ограничения на работу с SMS, но отправка через `SmsManager` разрешена при наличии SEND_SMS.
- **iOS**: автоматическая массовая отправка SMS без участия пользователя **фактически невозможна** (обычно открывается composer с подтверждением). Если критично “автоматически”, iOS либо исключаем из MVP, либо меняем канал (push/IM/email) или используем серверный SMS‑шлюз.

### 1.3. Нефункциональные требования (минимум)
- Надежность отправки: очередь, ретраи, паузы между сообщениями, ограничение скорости.
- Безопасность: авторизация, TLS, минимизация хранения персональных данных на устройстве.
- Аудит: кто и когда делал рассылку, текст, группы, количество адресатов.
- Масштаб: количество контактов в группах (например, 10, 1000, 50 000) — влияет на синхронизацию и стратегию.

### 1.4. Юридические/комплаенс аспекты
- Согласия на рассылку, хранение персональных данных, логирование текста/телефонов, локальные требования (GDPR/152‑ФЗ).
- Ограничения операторов на массовые SMS с SIM (антиспам‑фильтры, лимиты).

## 2) Целевая архитектура решения

### 2.1. Компоненты
1. **Mobile App (Android)**
    - UI выбора групп, ввода текста, запуск рассылки
    - Локальная очередь отправки
    - Отправка SMS через SIM (`SmsManager`)
    - Сбор статусов отправки/доставки (опционально)
    - Отправка логов/статусов на сервер
2. **Backend API**
    - Пользователи, роли (User/Admin)
    - Группы, контакты в группах
    - Кампании/рассылки (создание факта рассылки, хранение текста, статистика)
    - Журнал событий/аудит
3. **Admin Web (или готовая админка)**
    - Создание групп, импорт контактов, обновление состава
    - Управление доступами (какие группы видит пользователь/подразделение)

### 2.2. Модель данных (концептуально)
- `User(id, login, role, status, ...)`
- `Group(id, name, description, ownerOrg, ...)`
- `GroupMember(groupId, phone, name?, externalId?, validFrom/To?)`
- `Campaign(id, userId, createdAt, messageText, groups[], totalRecipients, status)`
- `CampaignRecipient(campaignId, phone, sendStatus, errorCode, sentAt, deliveredAt?)`

## 3) Проработка UX/UI (простое приложение)

### 3.1. Экраны MVP
1. **Логин** (или SSO/OTP — по безопасности)
2. **Список групп**
    - поиск, мультивыбор, счетчик адресатов (если отдаём сервером)
3. **Сообщение**
    - поле ввода, счетчик символов, предупреждение о сегментации (SMS 160/70)
4. **Подтверждение**
    - итог: групп/адресатов/примерный объём SMS (с учетом сегментов)
5. **Экран отправки (прогресс)**
    - отправлено/осталось/ошибки, кнопка “Пауза/Продолжить/Отменить”
6. **История**
    - список рассылок, детализация ошибок (минимально)

### 3.2. UX‑нюансы
- Предупреждение о тарифах и лимитах, подтверждение перед массовой отправкой.
- Ограничение максимального числа получателей/сообщений (конфигом с сервера).

## 4) Требования к Backend API

### 4.1. Основные эндпойнты (пример)
- `POST /auth/login` → access token (JWT/opaque)
- `GET /groups` → группы, доступные пользователю
- `GET /groups/{id}` → метаданные + (опционально) количество контактов
- `GET /groups/{id}/members?cursor=...` → список телефонов (постранично)
- `POST /campaigns` → создание кампании (userId, groupIds, messageText)
- `POST /campaigns/{id}/events` → статусы отправки по телефонам (batch)
- `GET /campaigns?from=...` → история пользователя

### 4.2. Важные технические решения
- **Постраничная выдача контактов** (cursor pagination), чтобы не тянуть тысячи номеров одним ответом.
- **Версионирование групп** (etag/updatedAt), чтобы кешировать и понимать изменения.
- **Конфиг с сервера**: лимиты, скорость, максимальный размер кампании, allowed hours.

## 5) Мобильная логика отправки SMS (ключевой блок)

### 5.1. Очередь и фоновые задачи
- Реализация отправки как **очередь задач** (Room DB + WorkManager/Foreground Service).
- Для долгих рассылок — **Foreground Service** с постоянным уведомлением (Android требования).

### 5.2. Контроль скорости и устойчивость
- Пауза между SMS (например, 200–1000 мс) + адаптивно по ошибкам оператора.
- Ретраи при временных ошибках (no service, radio off), но с лимитом.
- Возможность “прервать и продолжить позже”.

### 5.3. Статусы
- `SENT` (отправлено в модем) — через PendingIntent `SMS_SENT`
- `DELIVERED` (доставлено) — через `SMS_DELIVERED` (не всегда надежно/доступно)
- Ошибки: нет сети, airplane mode, недостаточно средств, generic failure, denied.

### 5.4. Сегментация сообщений
- Длинные тексты разбиваются на части (Multipart SMS).  
  В UI показывать “будет отправлено N SMS на одного получателя”.

### 5.5. Разрешения и политика
- Запрос SEND_SMS при первом запуске отправки + объяснение.
- На Android 13+ — отдельные нюансы уведомлений (POST_NOTIFICATIONS).

## 6) Безопасность и доступы

### 6.1. Аутентификация/авторизация
- JWT + refresh token, привязка к организации/ролям.
- На сервере: проверка доступа к группам.
- На клиенте: не хранить телефоны долговременно без необходимости.

### 6.2. Защита данных
- TLS, certificate pinning (по необходимости).
- Шифрование чувствительных данных на устройстве (EncryptedSharedPreferences/SQLCipher — по критичности).
- Логи без телефонов или с маскированием (по требованиям комплаенса).

## 8) План работ по этапам (Roadmap)

### Этап 0 — Подготовка (1–2 недели)
- Сбор требований, формализация ограничений (Android-only или кроссплатформа)
- Прототип UI (Figma)
- Архитектурное решение и ADR (Android: WorkManager + Foreground Service, Room)
- Спецификация API (OpenAPI)

### Этап 1 — Backend MVP (2–4 недели)
- Авторизация, пользователи, роли
- Группы и участники групп, постраничная выдача
- Создание кампаний и прием статусов
- Мини‑админка (хотя бы UI для импорта/CRUD) или интеграция с существующей

### Этап 2 — Mobile MVP (3–6 недель)
- Логин, список групп, выбор, экран сообщения
- Создание кампании на сервере
- Загрузка контактов (постранично) в момент рассылки
- Очередь отправки, Foreground Service, прогресс
- Отправка статусов пачками на сервер

### Этап 3 — Надежность и контроль (2–4 недели)
- Пауза/продолжение/отмена
- Ретраи и обработка ошибок
- Ограничения скорости/времени отправки (quiet hours)
- История рассылок в приложении

### Этап 4 — Полировка и релиз (2–3 недели)
- Нагрузочное тестирование API, оптимизация
- UX‑тестирование, локализация, accessibility
- Подготовка публикации (если Google Play: политика SMS permissions очень строгая — может потребоваться Enterprise‑distribution или закрытый канал)

## 10) Риски и решения заранее
1. **Блокировки/лимиты оператора** → ограничение скорости, лимиты кампаний, предупреждения.
2. **Политики магазинов** (SMS permission) → заранее выбрать модель распространения (MDM/enterprise/private).
3. **Большие группы** → постраничная выдача, потоковая обработка, не держать всё в памяти.
4. **Дедупликация при выборе нескольких групп** → серверная агрегация уникальных телефонов или клиентская (лучше сервером, чтобы контролировать аудит).
5. **iOS** → либо отдельный продукт с ручным подтверждением, либо смена архитектуры (SMS‑шлюз).
