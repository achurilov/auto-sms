### 1. Анализ предметной области и сбор требований

#### 1.1. Бизнес-цели:
*   Предоставить сотрудникам в "полях" (курьерам, торговым представителям, монтажникам) простой инструмент для быстрой коммуникации с группами клиентов/партнеров.
*   Обеспечить работу без постоянного доступа к интернету на этапе отправки сообщения.
*   Централизованно управлять контактными группами, избегая хаоса в телефонных книгах сотрудников.

#### 1.2. Акторы (Пользователи):
*   **Мобильный пользователь:** Сотрудник компании. Использует приложение для рассылки сообщений по готовым группам через свою SIM-карту.
*   **Администратор системы:** Ответственный за управление контактами. Работает с веб-интерфейсом сервера для создания/редактирования групп.

#### 1.3. Функциональные требования (User Stories):

**Для мобильного пользователя:**
> **US-01: Авторизация.** Как мобильный пользователь, я хочу входить в приложение по номеру телефона (через SMS-код), чтобы система могла загрузить мои контактные группы.
>
> **US-02: Просмотр групп.** Как мобильный пользователь, я хочу видеть список доступных мне групп контактов с названиями, назначенными администратором, чтобы выбрать нужную для рассылки.
>
> **US-03: Выбор нескольких групп.** Как мобильный пользователь, я хочу иметь возможность выбрать одну или несколько групп одновременно, чтобы отправить одно сообщение всем получателям из этих групп.
>
> **US-04: Создание сообщения.** Как мобильный пользователь, я хочу вводить текст СМС в многострочном поле, видя счетчик символов (лимит ~70/160 знаков), чтобы контролировать длину сообщения.
>
> **US-05: Отправка сообщения.** Как мобильный пользователь, после нажатия кнопки "Отправить", я хочу, чтобы приложение последовательно отправило СМС-сообщение каждому контакту из выбранных групп через мою SIM-карту, показывая индикатор прогресса.
>
> **US-06: Просмотр статуса.** Как мобильный пользователь, я хочу видеть экран со статусом последней рассылки (например: "В очереди...", "Отправлено: 15/50", "Ошибка: 2"), чтобы понимать прогресс операции.

**Для администратора:**
> **US-07: Управление группами.** Как администратор, я хочу создавать, редактировать и удалять группы контактов через веб-панель.
>
> **US-08: Управление контактами.** Как администратор, я хочу добавлять, импортировать (из CSV) и удалять контакты внутри групп. У каждого контакта должен быть как минимум `Имя` и `Номер телефона`.
>
> **US-09: Назначение прав.** Как администратор, я хочу назначать доступные группы конкретным пользователям (по их номерам телефонов).

#### 1.4. Нефункциональные требования:
*   **Производительность:** Отображение списка из >1000 контактов в группе не должно вызывать зависаний интерфейса (использовать пагинацию/ленивую подгрузку). Сама рассылка ограничена скоростью работы модема телефона (~1-2 смс/сек).
*   **Надежность:** Приложение должно корректно обрабатывать прерывания (звонок, потеря сети). При восстановлении связи рассылка должна либо продолжаться, либо предоставить пользователю отчет о статусе.
*   **Безопасность:** Номера телефонов пользователей не должны храниться в открытом виде на устройстве. Коммуникация между приложением и сервером — только по HTTPS.
*   **Совместимость:** Android 8+ и iOS 14+. Особое внимание уделить работе с разрешениями (`android.permission.SEND_SMS`, `READ_PHONE_STATE`) согласно современным политикам ОС.

### 2. Проектирование архитектуры

Это классическое клиент-серверное приложение.

#### 2.1. Мобильное приложение (Client)
*   **Платформы:** Разработка нативных приложений предпочтительнее для лучшей интеграции с системой.
    *   **Android:** Kotlin + Jetpack Compose/SwiftUI-подобный декларативный UI. Использование WorkManager для фоновых задач (если потребуется повторная отправка).
    *   **iOS:** Swift + SwiftUI.
*   **Альтернатива:** Кроссплатформенная разработка (Flutter / React Native) для экономии бюджета и времени. Позволяет использовать единую кодовую базу.
*   **Ключевой компонент:** Интеграция с API телефонии устройства (`SmsManager` на Android, `MFMessageComposeViewController` на iOS). Важно реализовать пакетную отправку, а не открывать стандартный интерфейс сообщений для каждого контакта.

#### 2.2. Серверная часть (Server)
*   **Язык/Фреймворк:** Современный стек, например, Python (FastAPI/Django), Go, Node.js (NestJS). Главное — производительность API и удобство работы с БД.
*   **База данных:** PostgreSQL. Идеально подходит для хранения реляционных данных (пользователи, группы, контакты - связь многие-ко-многим).
*   **Архитектура:** Чистая архитектура (*Clean Architecture*) или Hexagonal. Отделение бизнес-логики от фреймворка.
*   **Аутентификация:** Stateless-аутентификация через JWT-токены. Пользователь вводит номер -> получает SMS-код -> приложение подтверждает код на сервере -> сервер выдает JWT.
*   **API:** RESTful JSON API.

#### 2.3. Административная панель (Admin Panel)
*   Веб-приложение (SPA).
*   **Стек:** React/Vue.js + любой UI Kit (Material-UI, Ant Design).
*   Общается с тем же бэкендом, что и мобильное приложение, но использует эндпоинты с префиксом `/admin/*`, защищенные отдельной ролью.

### 3. План разработки (Roadmap)

Разбиваем на двухнедельные спринты (Agile/Scrum).

#### Фаза 1: Ядро системы (Sprints 1-4)

*   **Sprint 1: Инфраструктура и аутентификация.**
    *   Настройка CI/CD, репозиториев.
    *   Реализация модели БД (Users, Groups, Contacts, UserGroupsPermissions).
    *   API регистрации/авторизации по номеру телефона (+ интеграция с SMS-шлюзом для отправки кодов).
*   **Sprint 2: Админ-панель: CRUD для групп и контактов.**
    *   Интерфейс для управления группами.
    *   Интерфейс для добавления/удаления контактов.
    *   Backend-эндпоинты для этих операций.
*   **Sprint 3: Мобильное приложение: Авторизация и загрузка данных.**
    *   Экраны входа.
    *   Логика получения JWT и его сохранения.
    *   Загрузка и отображение списка групп с сервера.
*   **Sprint 4: Мобильное приложение: Выбор и подготовка сообщения.**
    *   Экран выбора групп (с множественным выбором).
    *   Экран ввода текста сообщения с подсчетом символов.

#### Фаза 2: Ключевая функциональность (Sprints 5-6)

*   **Sprint 5: Сердце системы — Рассылка.**
    *   **Backend:** Эндпоинт `/api/v1/send-sms` который принимает ID групп и текст. Он валидирует запрос и возвращает job_id.
    *   **Mobile:** Сбор всех уникальных номеров из выбранных групп на клиенте. Последовательная отправка через нативный API. Отображение progress bar'а. Сохранение истории рассылки локально.
*   **Sprint 6: Обратная связь и надежность.**
    *   **Backend:** Асинхронная обработка статусов невозможна (т.к. шлюз — это SIM-карта), но можно логировать сам факт запроса на отправку.
    *   **Mobile:** Экран "История рассылок". Детальный отчет по каждой рассылке ("Успешно", "Не удалось"). Механизм повторной отправки неудачных сообщений.

#### Фаза 3: Полировка и релиз (Sprints 7-8)

*   **Sprint 7: Обработка ошибок и edge cases.**
    *   Состояния отсутствия интернета.
    *   Отсутствие разрешений на отправку SMS.
    *   Пустой результат при выборе групп.
    *   Оптимизация расхода батареи во время долгой рассылки.
*   **Sprint 8: Тестирование, публикация, документация.**
    *   Внутреннее альфа- и бета-тестирование.
    *   Подготовка скриншотов и описаний для App Store / Google Play.
    *   Написание инструкций для администратора.

### 4. Технические риски и пути их минимизации

| Риск | Вероятность | Влияние | Стратегия митигации |
| :--- | :--- | :--- | :--- |
| **1. Блокировка SIM-карты оператором за спам.** | Высокая | Критическое | **Техническое ограничение:** ввести лимиты на количество сообщений в единицу времени (например, не более N штук в минуту). Вывести предупреждение пользователю. Это самая важная часть. |
| **2. Проблемы с разрешениями на отправку SMS (особенно на Android 13+).** | Средняя | Высокое | Провести глубокое исследование новых политик безопасности. Реализовать максимально понятные диалоги для пользователя, объясняющие, зачем нужно разрешение. Протестировать на разных версиях ОС. |
| **3. Долговременная рассылка блокирует основной поток (UI freeze).** | Низкая | Среднее | Выполнять цикл отправки в корутине (Kotlin) / OperationQueue (iOS) / фоне. Корректно обновлять UI через механизм состояний (StateFlow/Livedata, @Published). |
| **4. Расхождение данных (админ удалил группу, у юзера она еще есть).** | Средняя | Низкое | Не хранить группы статично. Перед началом формирования списка получателей делать легкий запрос на актуализацию состава выбранной группы. |

Этот план является основой. Дальнейшая детализация будет происходить уже в процессе работы команды в таск-трекере (Jira/Youtrack).
